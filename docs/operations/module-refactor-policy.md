# モジュール見直しポリシー

このポリシーは、新しい再利用モジュールを後から導入する際の対応を定義します。

## 1) モジュール新設・改修のトリガー
次のいずれかに該当した場合、共通モジュールを新設または改修します。
- 類似するリソース構成が 2 つ以上のシナリオに出現する
- セキュリティ/ガバナンス制御が複数シナリオで重複する
- 命名/タグ付けロジックが重複する

補足:
- 対象リソースに AVM が存在する場合は、カスタムモジュール新設より AVM 採用を優先する。
- AVM で不足する要件がある場合のみ、最小の差分をラッパーモジュールで補完する。

## 2) 既存 IaC 見直しの必須ルール
新しいモジュールを追加した場合、既存 IaC を必ず見直します。

必須アクション:
1. 同等のインライン実装を使っているシナリオを洗い出す。
2. 安全に置き換え可能な重複ブロックをモジュール呼び出しに変更する。
3. 明示承認がない限り、シナリオの挙動は変更しない。
4. シナリオ文書にモジュール依存の追記を行う。

## 3) 見直し実施フロー
1. 最小パラメータでモジュール I/F を設計する。
2. まず 1 つのパイロットシナリオへ適用する。
3. 挙動およびコスト/セキュリティ影響を検証する。
4. 問題なければ他シナリオへ展開する。
5. 廃止対象のインライン実装を削除する。
6. AVM 未適用の残件がある場合は、各シナリオ README に理由と移行条件を更新する。

## 4) モジュールのパラメータ予算
モジュール I/F は厳密かつ小さく保ちます。

必須パラメータ:
- `scenarioCode`
- `location`（省略時は呼び出し元の既定値を使用）

任意パラメータ（高い価値がある場合のみ）:
- コスト/性能に実質影響する SKU やサイズ
- テナント差分に対応するガバナンス上書きフラグ

公開しない項目:
- 見た目だけの命名要素
- 既定で扱えるネットワーク範囲
- 推論可能なリソース単位の細かなスイッチ
